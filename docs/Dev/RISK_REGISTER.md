# Pillar Risk Register

## 1. Scope

| Item                              | Definition                                                                                                                                                                                                                                       |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Purpose                           | Project-level risk register for Pillar delivery, operations, commercial readiness, and regulated-market adoption.                                                                                                                                |
| Product frame                     | Pillar is the Stripe-grade API and operations layer for Canton-backed assets.                                                                                                                                                                    |
| Source-of-truth stance            | Canton Ledger remains the economic source of truth; Pillar DB remains Projection / Audit / Config only.                                                                                                                                          |
| Distinct from regression contract | [REGRESSION_CONTRACT.md](./REGRESSION_CONTRACT.md) defines non-negotiable invariants and merge blockers. This register tracks probabilistic risks and response plans.                                                                            |
| Distinct from threat model        | [THREAT_MODEL.md](./THREAT_MODEL.md) is expected to focus on adversarial/security threats. This register includes technical, vendor, regulatory, delivery, market, and operational risk.                                                         |
| Primary operating references      | [README.md](./README.md), [DECISIONS.md](./DECISIONS.md), [DATA_MODEL.md](./DATA_MODEL.md), [API_MATRIX.md](./API_MATRIX.md), [EVENT_CATALOG.md](./EVENT_CATALOG.md)                                                                             |
| Architecture references           | [12 Security](../Architecture/12_Security.md), [18 Deployment](../Architecture/18_Deployment.md), [22 Pillar Observability](../Architecture/22_Pillar%20Observability.md), [23 Implementation Plan](../Architecture/23_Implementation%20Plan.md) |
| Phase coverage                    | [P0](./Phase_00_Foundation.md) through [P14](./Phase_14_Usage_Metering_Billing.md)                                                                                                                                                               |
| Tracking threshold                | Risks with exposure >= 9 are tracked in this register; risks with exposure >= 15 require active owner review at each phase gate.                                                                                                                 |

| Out of scope                                         | Why                                                                                                                 |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Per-PR defects                                       | Covered by tests, reviews, and [REGRESSION_CONTRACT.md](./REGRESSION_CONTRACT.md).                                  |
| Exploit-level attacker paths                         | Covered by [THREAT_MODEL.md](./THREAT_MODEL.md) once authored and by [Phase 08](./Phase_08_Security_Compliance.md). |
| Individual customer implementation tasks             | Tracked in onboarding tickets unless they affect platform risk.                                                     |
| Generic startup risk with no Pillar-specific trigger | Not actionable for engineering governance.                                                                          |

## 2. Risk scoring scale

| Field       | Scale                | Meaning                                                                                               |
| ----------- | -------------------- | ----------------------------------------------------------------------------------------------------- |
| Probability | 1                    | Rare: unlikely without major external change.                                                         |
| Probability | 2                    | Uncommon: possible during long program execution.                                                     |
| Probability | 3                    | Plausible: credible during normal delivery or first customer ramp.                                    |
| Probability | 4                    | Likely: expected unless mitigated early.                                                              |
| Probability | 5                    | Near-certain: already visible or structurally unavoidable.                                            |
| Impact      | 1                    | Minor: local rework, no launch or trust impact.                                                       |
| Impact      | 2                    | Moderate: phase delay, bounded operational pain, customer-visible workaround.                         |
| Impact      | 3                    | Serious: blocks a phase gate, materially degrades SLO, or requires customer communication.            |
| Impact      | 4                    | Severe: blocks GA, breaks regulated-customer acceptance, or creates major operational incident.       |
| Impact      | 5                    | Critical: threatens product viability, ledger correctness, legal acceptance, or major customer trust. |
| Exposure    | Probability x Impact | 1-25 numeric score used for prioritization.                                                           |

| Exposure band | Label    | Governance action                                                                       |
| ------------- | -------- | --------------------------------------------------------------------------------------- |
| 1-4           | Watch    | Keep in phase failure-mode sections; no central review required.                        |
| 5-8           | Monitor  | Track in owning phase; revisit at phase entry and exit.                                 |
| 9-14          | Managed  | Track here with owner, mitigation link, trigger, contingency.                           |
| 15-19         | High     | Review at every phase gate and release readiness meeting.                               |
| 20-25         | Critical | Executive escalation; no GA promotion while trigger is active and contingency untested. |

| Mitigation status | Definition                                                                            |
| ----------------- | ------------------------------------------------------------------------------------- |
| Proposed          | Response exists only as a plan or ticket reference.                                   |
| Planned           | Ticket/runbook exists and is assigned to a phase.                                     |
| In progress       | Implementation or operational procedure is being built.                               |
| Controlled        | Mitigation is implemented and verified by a gate, runbook drill, or regression check. |
| Accepted          | Risk remains intentionally tolerated with explicit owner and monitoring.              |

| Class       | Minimum mitigation evidence                                                                                   | Example escalation owner | Review artifact                                                             |
| ----------- | ------------------------------------------------------------------------------------------------------------- | ------------------------ | --------------------------------------------------------------------------- |
| Technical   | Regression test, chaos drill, benchmark, compatibility matrix, or rebuild proof.                              | Engineering lead         | Phase gate evidence, [VERIFICATION.md](./VERIFICATION.md), service runbook. |
| Vendor      | Version pin, fallback path, provider SLA monitor, fail-open/fail-closed decision, or alternate provider plan. | Platform lead            | Vendor review note, incident review, release checklist.                     |
| Regulatory  | Counsel-approved rule, audit export profile, retention policy, evidence manifest, or fail-closed workflow.    | Compliance lead          | Compliance decision record, audit export sample, phase gate signoff.        |
| Delivery    | Dependency graph, phase boundary decision, owner assignment, or ticket split.                                 | Program owner            | Phase checklist, ADR, verification entry.                                   |
| Market      | Customer discovery evidence, deployment-mode parity proof, pricing evidence, or onboarding feedback.          | Product lead             | Onboarding review, pricing review, customer-risk note.                      |
| Operational | SLO burn alert, runbook drill, incident review, dashboard, or paging policy.                                  | SRE lead                 | Runbook, incident review, SLO report.                                       |

| Owner responsibility  | Required behavior                                                                                                       |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Score stewardship     | Keep probability and impact tied to observed evidence, not optimism.                                                    |
| Trigger definition    | Keep trigger concrete enough for an alert, phase gate, customer escalation, or review finding.                          |
| Contingency readiness | Ensure contingency can be executed by someone other than the author.                                                    |
| Link maintenance      | Keep mitigation links live and specific; phase-level links are acceptable only when a narrower ticket is not available. |
| Review attendance     | Attend review when risk exposure is >= 15 or when the risk trigger is active.                                           |
| Closure discipline    | Do not delete risk IDs; move status to Controlled or Accepted and retain mapping.                                       |

| Evidence type          | Acceptable for Controlled status                                                    | Not acceptable alone                                  |
| ---------------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------- |
| Automated verification | Passing test, golden scan, benchmark, chaos scenario, migration verification.       | Local compile without scenario coverage.              |
| Operational drill      | Runbook executed against staging/sandbox with captured outcome.                     | Runbook written but never exercised.                  |
| Vendor resilience      | Failover, retry, pinning, or degraded-mode test against simulated provider failure. | Provider status-page link only.                       |
| Regulatory control     | Counsel-approved policy, audit manifest, export sample, or decision log.            | Informal product assumption.                          |
| Delivery control       | Dependency cycle removed, phase gate passed, owner assigned, or ADR accepted.       | Meeting note with no artifact.                        |
| Market control         | Customer acceptance signal, documented objection handling, or pricing evidence.     | Anecdotal enthusiasm without decision-maker evidence. |

| Trigger severity | Handling                                                                                                                             |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Early warning    | Owner updates status and mitigation date at next weekly delivery review.                                                             |
| Active trigger   | Owner starts contingency and notifies phase/release owner the same day.                                                              |
| Phase blocker    | Phase cannot exit until trigger is cleared, accepted by escalation owner, or moved behind a documented launch guardrail.             |
| Release blocker  | Release cannot proceed until contingency is tested or the risk is explicitly accepted by product, engineering, and the domain owner. |
| Incident trigger | Incident commander references risk ID in incident notes and drives post-incident register update.                                    |

## 7. Review cadence

| Cadence                | Participants                                                        | Scope                                                                              | Required output                                                                                                        |
| ---------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Phase entry            | Phase owner, engineering lead, product/compliance/SRE as applicable | Risks mapped to the phase plus exposure >= 15 risks                                | Confirm owner, trigger, contingency, and ticket/runbook link before ticket execution starts.                           |
| Phase exit             | Phase owner, reviewer, SRE/security/compliance where applicable     | New or changed risk exposure; mitigation evidence from gates                       | Update exposure or status; block promotion if active high-risk trigger lacks tested contingency.                       |
| Weekly delivery review | Program owner, phase owners                                         | Delivery, dependency, staffing, and top-10 drift                                   | Re-rank top-10 if probability/impact changes; open phase-scoped tickets for new mitigations.                           |
| Release readiness      | Engineering, SRE, security, compliance, product                     | All exposure >= 15 risks and all risks with active triggers                        | Accept, mitigate, or block release; document decision in [VERIFICATION.md](./VERIFICATION.md) if verification-related. |
| Incident review        | Incident commander, affected service owner, SRE lead                | Triggered operational/technical/vendor risks                                       | Add or revise runbook, alert, test, or phase ticket; update probability/impact if recurrence changed.                  |
| Quarterly governance   | Product, counsel/compliance, engineering, GTM                       | Regulatory and market risks, deployment-mode demand, pricing, vendor concentration | Revalidate asset scope, jurisdiction scope, vendor posture, and commercial assumptions.                                |

| Risk update rule | Requirement                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------------- |
| New risk         | Add when exposure >= 9 or when an owner asks for release/governance visibility.                   |
| Score change     | Update probability or impact when evidence changes, not because mitigation is desired.            |
| Status change    | Only move to Controlled after a test, runbook drill, gate, or operational evidence exists.        |
| Closure          | Do not delete; mark Accepted or Controlled and keep historical ID stable.                         |
| Link hygiene     | Every managed risk must keep at least one ticket, phase, ADR, contract, catalog, or runbook link. |

## 8. Escalation rules

| Condition                                                          | Escalation                                     | Required action                                                                                            |
| ------------------------------------------------------------------ | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Exposure >= 20                                                     | Executive/product/engineering escalation       | No GA promotion while trigger is active; contingency must be tested or explicitly accepted.                |
| Exposure >= 15 and trigger active                                  | Phase owner plus relevant domain lead          | Stop promotion for affected phase or release until mitigation owner signs response.                        |
| Any risk threatens README §0 invariant                             | Engineering lead and reviewer                  | Treat as regression-contract concern; block merge/release until invariant is restored.                     |
| Any risk threatens legal/regulatory compliance                     | Compliance lead and product counsel            | Fail closed for regulated workflows; preserve audit evidence and customer/regulator communication trail.   |
| Any risk threatens ledger correctness                              | Ledger runtime lead, projection lead, SRE lead | Stop command submission for affected flow, preserve trace evidence, reconcile from ledger source of truth. |
| Any risk threatens public `/v1` grammar                            | API contract lead                              | Block public release; require OpenAPI/golden/SDK/event contract review.                                    |
| Vendor outage affects hot path                                     | SRE lead and vendor owner                      | Enter degraded mode if safe, invoke vendor contingency, update status/customer communication.              |
| On-call exhaustion or alert fatigue persists for two review cycles | Engineering lead and SRE lead                  | Reduce release load, remove non-actionable pages, fund automation/runbook repair before feature expansion. |
| Customer-facing incident maps to a registered risk                 | Incident commander                             | Reference risk ID in incident review and update trigger/contingency if response differed.                  |
| New architecture decision changes top-10 risk                      | Program owner                                  | Add/supersede ADR as needed and re-score related risks in the next review.                                 |

| Escalation artifact | Use                                                                                                           |
| ------------------- | ------------------------------------------------------------------------------------------------------------- |
| Risk ID             | Stable reference in incident notes, release readiness, phase reviews, and customer-facing internal summaries. |
| Related tickets     | Implementation and verification route for mitigation.                                                         |
| Trigger             | Observable condition that changes risk from tracked to active.                                                |
| Contingency         | Pre-agreed response; if not executable, create runbook or phase ticket.                                       |
| Owner               | Single accountable role for score, mitigation status, and escalation response.                                |
