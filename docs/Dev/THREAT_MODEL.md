# Pillar Threat Model

## 1. Scope and method

This document is the operational threat model for Pillar Mission Control. It uses STRIDE per trust boundary and treats [Phase 08 Security / Compliance](./Phase_08_Security_Compliance.md#3-architecture) as the canonical trust-boundary source. It extends that boundary with the runtime, projection, webhook, registry, search/export, and usage-meter services introduced by the phase plan and architecture set.

| Item                              | Binding source                                                                                                                                                                                                                                                                                                                                                         | Threat-model interpretation                                                                                                                       |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ledger authority                  | [README invariant 1](./README.md#cross-phase-invariants-never-violate), [ADR-0001](./DECISIONS.md#adr-0001-canton-ledger-as-sole-source-of-truth), [IC-01](./REGRESSION_CONTRACT.md#2-invariant-clauses-numbered-atomic-testable)                                                                                                                                      | Threats that make DB or search/export output authoritative are high impact even when customer-visible data appears correct.                       |
| DB role                           | [README invariant 2](./README.md#cross-phase-invariants-never-violate), [ADR-0005](./DECISIONS.md#adr-0005-projection--audit--config-split-for-pillar-postgres), [IC-02](./REGRESSION_CONTRACT.md#2-invariant-clauses-numbered-atomic-testable)                                                                                                                        | Pillar DB compromise is modeled as projection/audit/config compromise, not ledger compromise, unless the attacker can influence command planning. |
| Public API invisibility           | [README invariant 3](./README.md#cross-phase-invariants-never-violate), [ADR-0002](./DECISIONS.md#adr-0002-billing-style-external-api-surface-canton-internals-hidden), [IC-03](./REGRESSION_CONTRACT.md#2-invariant-clauses-numbered-atomic-testable)                                                                                                                  | Leaking Canton identifiers is information disclosure and can become elevation when paired with participant credentials.                           |
| Intent and command trace          | [README invariants 4-5](./README.md#cross-phase-invariants-never-violate), [ADR-0003](./DECISIONS.md#adr-0003-intent-first-write-path), [ADR-0011](./DECISIONS.md#adr-0011-command_id-derivation-spec), [IC-04](./REGRESSION_CONTRACT.md#2-invariant-clauses-numbered-atomic-testable), [IC-05](./REGRESSION_CONTRACT.md#2-invariant-clauses-numbered-atomic-testable) | Duplicate, missing, or forged trace edges are tampering and repudiation threats, not merely observability defects.                                |
| Projection and webhook authority  | [README invariants 6-7](./README.md#cross-phase-invariants-never-violate), [ADR-0006](./DECISIONS.md#adr-0006-webhook-first-async-with-hmac-sha256-signing-and-per-endpoint-version-pinning), [IC-06](./REGRESSION_CONTRACT.md#2-invariant-clauses-numbered-atomic-testable), [IC-07](./REGRESSION_CONTRACT.md#2-invariant-clauses-numbered-atomic-testable)           | Events and webhooks must be generated from projection state, signed, retried, and replayable.                                                     |
| Deployment neutrality             | [README invariant 8](./README.md#cross-phase-invariants-never-violate), [ADR-0010](./DECISIONS.md#adr-0010-deployment-mode-independence-hosted--customer-validator--self-hosted-share-identical-v1-grammar), [IC-08](./REGRESSION_CONTRACT.md#2-invariant-clauses-numbered-atomic-testable), [18 Deployment](../Architecture/18_Deployment.md)                         | Hosted, customer-validator, and self-hosted may shift operational responsibility, but threat mitigations must preserve identical `/v1` semantics. |
| Search/export/reporting           | [Phase 11](./Phase_11_Search_Export_Reporting.md), [21 Search Data Export Reporting](../Architecture/21_Search%20Data%20Export%20Reporting.md)                                                                                                                                                                                                                         | Search indexes, exports, and reports are derived artifacts with extra disclosure risk and no economic authority.                                  |
| Template registry / DAR lifecycle | [Phase 12](./Phase_12_Template_Registry_Versioning.md), [17 Template Registry Versioning](../Architecture/17_Template%20Registry%20Versioning.md)                                                                                                                                                                                                                      | DAR provenance, signing, rollout, rollback, and package compatibility are supply-chain boundaries.                                                |
| Usage metering / billing          | [Phase 14](./Phase_14_Usage_Metering_Billing.md)                                                                                                                                                                                                                                                                                                                       | Usage records are financially relevant audit data derived from request, ledger, projection, webhook, and export traces.                           |

Method:

| Step | Procedure                                                          | Output                                                                      |
| ---- | ------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| 1    | Enumerate trust boundaries from Phase 08 and runtime architecture. | Boundary list in §3.                                                        |
| 2    | Apply STRIDE at each boundary.                                     | Threat catalog in §4.                                                       |
| 3    | Bind each threat to an existing ticket or invariant clause.        | Mitigation-ticket column and §9 mapping.                                    |
| 4    | Separate prevented risk from residual risk.                        | Residual-risk column and §10 open threats.                                  |
| 5    | Keep controls implementation-facing.                               | Tickets use `P<phase>.<area><nn>` IDs or `IC-xx` clauses, not vague policy. |

STRIDE shorthand:

| Letter | Category               | Pillar examples                                                             |
| ------ | ---------------------- | --------------------------------------------------------------------------- |
| S      | Spoofing               | forged API key identity, fake webhook source, fake participant endpoint     |
| T      | Tampering              | modified idempotency row, stale projection replay, altered DAR digest       |
| R      | Repudiation            | missing audit trace, unverifiable operator action, unsigned export manifest |
| I      | Information disclosure | PII in metadata, Canton internals in API, raw secrets in logs               |
| D      | Denial of service      | rate-limit bypass, queue starvation, participant unavailability             |
| E      | Elevation of privilege | scope bypass, party entitlement bypass, break-glass abuse                   |

## 3. Trust boundaries (with diagram)

```text
External customer / SDK / CLI
  |  HTTPS, API key, Idempotency-Key, Pillar-Version
  v
apps/api / API edge
  |  SQL, DB service role, idempotency lock, audit write
  v
Pillar DB: idempotency / audit / config / projection
  |  queued operation, workflow state, command request
  +-------------------------> services/workflow-orchestrator
  |                                  |
  |                                  v
  |                           services/compliance-adapter <----> KYC/AML vendor
  |
  v
services/ledger-command
  |  gRPC Ledger API, JWT, mTLS, stable command_id
  v
Canton participant
  |  protocol traffic, party rights, completion/update stream
  v
Canton synchronizer
  |
  +--> participant / PQS / update stream
             |
             v
      services/projection-worker
             |
             v
      Pillar projection DB
             |
             +--> apps/api read APIs
             +--> services/webhook-dispatcher ---> customer webhook endpoint
             +--> services/search-indexer -------> search index
             +--> services/export-worker --------> object storage / signed URL
             +--> services/usage-meter ----------> usage/billing data

services/template-registry
  |  signed DAR, package policy, rollout / rollback
  +--> services/ledger-command and deployment jobs
```

| Boundary ID | Boundary                                                         | Assets crossing                                               | Trust change                                          | Canonical controls                                                                         |
| ----------- | ---------------------------------------------------------------- | ------------------------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| B01         | Client ↔ API                                                     | API keys, idempotency keys, request body, metadata            | untrusted internet to authenticated public API        | TLS, API key hashing, scopes, rate limits, audit: `P8.K01`, `P8.K02`, `P8.K03`, `P8.K07`   |
| B02         | API ↔ idempotency/audit DB                                       | request hash, idempotency row, response snapshot, audit shell | app runtime to DB authority for retry/audit           | DB role scoping, tenant keys, trace view: `P3.D02`, `P3.D03`, `P3.D04`, `P4.E06`           |
| B03         | API ↔ workflow-orchestrator                                      | intent lifecycle, policy state, operation IDs                 | synchronous API acceptance to async workflow          | intent-first write path, audit correlation: `P4.E06`, `P8.K03`, IC-04                      |
| B04         | workflow-orchestrator ↔ compliance-adapter                       | KYC/AML decision request, evidence reference, vendor result   | internal workflow to external policy source           | adapter isolation, no direct ledger mutation: `P8.K04`, `P8.K05`, `P8.K07`                 |
| B05         | DB / queue ↔ ledger-command                                      | operation, command plan, command_id, submission_id            | persisted intent to ledger-facing runtime             | deterministic command ID, party entitlement check: `P4.F03`, `P4.F04`, `P4.F05`, `P8.K03`  |
| B06         | ledger-command ↔ participant                                     | JWT, mTLS cert, Daml commands, completions                    | Pillar runtime to Canton participant trust            | mTLS/JWT, participant affinity, canActAs/canReadAs: `P4.F02`, `P8.K06`, `P9.J02`           |
| B07         | participant ↔ synchronizer                                       | Canton protocol traffic, finality, ordering                   | participant node to Canton network                    | synchronizer health, HA, deployment profile: `P9.J02`, `P10.L01`, IC-01                    |
| B08         | participant/PQS ↔ projection-worker                              | update stream, offsets, contract payload projection inputs    | ledger event stream to derived DB state               | checkpointing, rebuild, reconciliation: `P5.G02`, `P5.G03`, `P5.G06`, `P5.G07`             |
| B09         | projection DB ↔ API reads                                        | balances, holdings, intents, events, as-of watermarks         | derived DB to customer-visible API                    | forbidden internals, watermarks, projection freshness: `P2.C03`, `P5.E07`, `P8.K07`        |
| B10         | projection/event outbox ↔ webhook-dispatcher ↔ customer endpoint | event payloads, endpoint secrets, delivery attempts           | trusted event builder to untrusted customer endpoint  | HMAC, timestamp, retries, DLQ, replay: `P6.H02`, `P6.H03`, `P6.H04`, `P6.H05`              |
| B11         | template-registry ↔ ledger-command / deploy jobs                 | DAR digest, signature, package version, rollout policy        | release supply chain to runtime package selection     | signature verification, rollback discipline: `P12.N01`, `P12.N02`, `P12.N05`, `P9.J03`     |
| B12         | projection DB ↔ search-indexer/export-worker/object storage      | search documents, export manifests, signed URLs               | derived DB to bulk data artifact                      | redaction, scoped jobs, manifests, signed URLs: `P11.M01`, `P11.M04`, `P11.M05`, `P11.M10` |
| B13         | runtime traces ↔ usage-meter                                     | request counts, command counts, webhook/export units          | operational telemetry to billable records             | usage derivation and audit: `P14.Q01`, `P14.Q02`, `P14.Q03`, `P8.K03`                      |
| B14         | operator/admin ↔ platform                                        | config changes, rotations, break-glass, trace expansion       | privileged human or automation to production controls | audit, least privilege, rotation drill, pen-test: `P8.K03`, `P8.K06`, `P8.K07`, `P10.L08`  |
