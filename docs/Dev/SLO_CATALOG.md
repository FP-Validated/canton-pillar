# Pillar SLO Catalog

## 1. Scope

This catalog defines every production SLI, target SLO, error budget, alert binding, owner, dashboard panel, runbook, phase ticket, and deployment-mode commitment for Pillar GA operations.

| Scope item     | Catalog commitment                                                                                         | Source of authority                                                                                                               |
| -------------- | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| SLI definition | Every SLO has a PromQL-compatible query over Pillar or Canton-exported metrics.                            | [22 Pillar Observability](../Architecture/22_Pillar%20Observability.md), [Phase 10](./Phase_10_GA_Hardening.md)                   |
| SLO target     | Targets are internal operational objectives; customer SLA terms may be lower and mode-specific.            | [22 Pillar Observability](../Architecture/22_Pillar%20Observability.md#pillar-운영-slo--sla-초안)                                 |
| Error budget   | Availability-style SLOs use `1 - target`; latency/freshness SLOs use bad-event ratio over eligible events. | [Phase 10 §5.2](./Phase_10_GA_Hardening.md#52-error-budget-policy)                                                                |
| Alert binding  | Every P0/P1 burn alert binds to an alert ID, owner, dashboard panel, and runbook under `RUNBOOKS/`.        | [Phase 10 P10.L04](./Phase_10_GA_Hardening.md#9-implementation-plan), [P10.L06](./Phase_10_GA_Hardening.md#9-implementation-plan) |
| Owner          | Owner labels route Alertmanager and release-freeze decisions.                                              | [Phase 10 P10.L03-L06](./Phase_10_GA_Hardening.md#9-implementation-plan)                                                          |
| Dashboard link | Panel IDs are stable Grafana UID/panel keys expected from `infra/observability/grafana`.                   | [Phase 10 P10.L03](./Phase_10_GA_Hardening.md#9-implementation-plan)                                                              |
| Runbook        | Paths are forward references to Wave 2 runbook files under `RUNBOOKS/`.                                    | [Phase 10 P10.L05](./Phase_10_GA_Hardening.md#9-implementation-plan)                                                              |
| Phase ticket   | Every SLO maps to at least one ticket, primarily `P10.L06`, and often the producing phase ticket.          | [README ticket scheme](./README.md#4-ticket-anatomy)                                                                              |

Operating invariants:

| Invariant                                                                       | SLO impact                                                                                                                    |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Canton Ledger is the single economic source of truth.                           | SLOs never treat projection rows as authoritative for asset movement; correctness SLOs compare projection to ledger evidence. |
| Pillar DB stores only Projection / Audit / Config.                              | SLO queries may read projection/audit/config metrics, never hidden authoritative balance state.                               |
| Public `/v1` is Canton-invisible.                                               | Customer-facing availability/latency SLOs are over developer-friendly API objects, not raw Canton endpoints.                         |
| Every mutation follows `intent -> operation -> command_id -> update_id/offset`. | Intent, ledger command, projection, webhook, audit, and reconciliation SLOs share trace labels.                               |
| Events are emitted from projected ledger state.                                 | Webhook SLOs are downstream of projection freshness and must not mask stale projection.                                       |
| Deployment mode changes wiring only.                                            | API grammar SLOs are equal across `hosted`, `customer-validator`, and `self-hosted`; ownership and exclusions differ.         |

### 3.1 SLO labels required on all metrics

| Label             | Required values                                                                           | Purpose                                                            |
| ----------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `env`             | `prod`, `sandbox`, `test`                                                                 | Keeps live-mode SLO budget distinct from sandbox/test diagnostics. |
| `deployment_mode` | `hosted`, `customer-validator`, `self-hosted`                                             | Enables mode-specific ownership without API grammar forks.         |
| `tenant_tier`     | `standard`, `enterprise`, `regulated`, `internal`                                         | Routes capacity planning and premium commitments.                  |
| `region`          | Cloud or customer region code                                                             | Supports blast-radius scoping.                                     |
| `owner_team`      | Catalog owner label                                                                       | Alertmanager route and release-freeze owner.                       |
| `slo`             | Exact SLO name                                                                            | Joins burn metrics, dashboards, tickets, and runbooks.             |
| `class`           | `platform`, `business_rejected`, `customer_error`, `operator_cancelled`, `not_applicable` | Enforces exclusion policy in PromQL.                               |

### 3.2 Exclusion policy

| Exclusion                                                                      | Applies to                                              | Does not excuse                                                                                                              |
| ------------------------------------------------------------------------------ | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Customer 4xx, authentication failure, validation failure, idempotency conflict | API availability and latency SLOs                       | API bugs that misclassify platform errors as 4xx.                                                                            |
| Customer webhook endpoint outage                                               | Platform webhook delivery success                       | Dispatcher failures, signing failures, missing events, or DLQ classifier failure.                                            |
| Planned maintenance with published window                                      | Availability/freshness budget if declared before impact | Data correctness, audit completeness, idempotency, command dedupe, or hidden stale balances.                                 |
| Operator-cancelled export/rebuild/release task                                 | Job success SLO denominator                             | Missing cancellation audit evidence.                                                                                         |
| Sandbox/test traffic                                                           | Production SLO budget                                   | Sandbox SLO dashboards and developer-experience regression reviews.                                                          |
| Canton network customer-operated outage in self-hosted/customer-validator mode | Pillar-managed infrastructure SLOs                      | Pillar software behavior, error classification, retry safety, status guidance, and projection recovery after ledger resumes. |

## 4. Error budget policy

| Budget state     | Trigger                                                                                                                                | Required action                                                                                 | Release posture                                                       | Owner                                 |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------- |
| Healthy          | `< 25%` budget consumed in 28d                                                                                                         | Normal deploy policy; monitor burn dashboards.                                                  | Normal release train.                                                 | SLO owner                             |
| Watch            | `25-50%` consumed or one P2 burn alert                                                                                                 | Review recent deploys, capacity, queue growth, and customer-impact scope.                       | Risky deploys require owner sign-off.                                 | SLO owner + release manager           |
| Constrained      | `50-75%` consumed or repeated P1 burn                                                                                                  | Freeze risky deploys for affected component; open corrective ticket; attach dashboard evidence. | Non-critical changes require incident commander approval.             | Incident commander                    |
| Freeze           | `75-100%` consumed or unresolved P1                                                                                                    | Freeze non-critical releases for affected component; run game-day if failure class is unclear.  | Only fixes, rollbacks, or risk-reducing deploys.                      | SRE lead + owner lead                 |
| Exhausted        | `>= 100%` consumed or P0 correctness incident                                                                                          | Stop production-affecting changes until incident review and corrective actions are accepted.    | Release train blocked for affected component.                         | Engineering lead + incident commander |
| Correctness stop | Any duplicate economic command, customer-visible reconciliation mismatch, audit gap, hidden stale balance, or unsigned trusted webhook | Treat as P0 regardless of percentage consumed.                                                  | Immediate freeze until root cause, proof, and regression guard exist. | Engineering lead                      |

Budget formulas:

| SLO type                  | Budget formula                                                                            | Bad-event definition                                                                                       |
| ------------------------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Availability/success rate | `budget = 1 - target`; `burn = bad_events / total_events / budget`                        | Platform 5xx, unclassified failures, command platform failures, missing audit traces, failed usage events. |
| Latency/freshness         | `bad_event_ratio = events_over_threshold / eligible_events`; `budget = allowed_bad_ratio` | Eligible event exceeds p99 threshold or stale classification deadline.                                     |
| Integrity/correctness     | No meaningful budget for customer-visible correctness; any event pages.                   | Confirmed ledger/projection mismatch, duplicate command, audit gap, idempotency replay divergence.         |
| Job throughput            | `bad_event_ratio = jobs_missed_deadline / eligible_jobs`                                  | Job timed out, missed standard deadline, failed without classified cause, or lacked completion event.      |
| Onboarding                | Cohort-based bad-event ratio                                                              | System-caused step failure, wizard dead-end, missing first-workflow verification.                          |

Policy details:

| Rule                     | Requirement                                                                                                                                   |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Budget accounting source | Prometheus SLO recording rules under `infra/observability/slo` from `P10.L06`.                                                                |
| Release gate integration | `P10.L08` readiness packet includes current budget state for every SLO in §3.                                                                 |
| Incident linkage         | Every P0/P1 budget burn creates an incident timeline entry with alert fingerprint, dashboard snapshot, runbook execution, and owner decision. |
| Customer communication   | `P10.L07` status page publishes customer-visible degradation without exposing Canton internals.                                               |
| Budget reset             | Budgets reset only by time-window rolloff, not by manual counter edits.                                                                       |
| Exception approval       | Temporary exclusion changes require SRE lead and engineering lead approval and an ADR if persistent.                                          |

Recording rules expected from `P10.L06`:

```promql
# Availability-style bad-event ratio.
slo:bad_event_ratio:5m{slo="pillar_api_5xx_rate"}
  = sum(rate(pillar_api_requests_total{env="prod",status=~"5.."}[5m]))
```

## 9. SLO review cadence

| Cadence                       | Participants                                                   | Inputs                                                               | Decisions                                                              | Output artifact                                           |
| ----------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------- | --------------------------------------------------------- |
| Daily on-call handoff         | Current and next on-call, incident commander if active         | P0/P1 alerts, budget burn, active incidents, deployment changes      | Continue, escalate, or downgrade active incidents.                     | Incident timeline entries and handoff note.               |
| Weekly SLO review             | SLO owners, SRE, release manager, support lead                 | 28d budget, 30d SLO rollup, top alerts, slow burns, customer tickets | Corrective tickets, release constraints, alert tuning proposals.       | Weekly SLO review record linked from readiness packet.    |
| Release readiness             | Engineering lead, SRE lead, security/compliance, product owner | All §3 SLO states, runbook rehearsal status, unresolved incidents    | Promote, defer, rollback, or freeze release.                           | `P10.L08` readiness packet.                               |
| Monthly target review         | Engineering leads, product, support, customer success          | SLO attainment, customer SLA terms, mode-specific failures           | Adjust internal targets, owner labels, dashboard panels, runbooks.     | Catalog patch plus ADR if policy changes.                 |
| Post-incident review          | Incident commander, SLO owner, affected service owners         | Incident timeline, trace evidence, budget burn, customer impact      | Root cause, corrective controls, regression tests, budget freeze exit. | Post-incident report linked to runbook execution.         |
| Quarterly architecture review | Staff engineers, SRE lead, security lead                       | Architecture drift, new phases, deployment-mode commitments          | Add/remove SLOs, change measurement model, update phase tickets.       | Catalog update and decision record if commitment changes. |

Review rules:

| Rule                                   | Requirement                                                                                                       |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| No orphan SLOs                         | Every SLO must retain owner, alert IDs, runbook, dashboard panel, and phase ticket.                               |
| No silent target changes               | Target or exclusion changes require review entry and readiness-packet acknowledgement.                            |
| No customer-visible correctness budget | Correctness incidents cannot be normalized by changing the percentage target.                                     |
| No runbook drift                       | Runbook links and commands are checked during release readiness and game-day rehearsal.                           |
| No mode ambiguity                      | Every review distinguishes Pillar-owned failure from customer-operated infrastructure failure where mode applies. |

## 10. Deployment-mode SLO differences

Canonical deployment modes are `hosted`, `customer-validator`, and `self-hosted`. The `/v1` API grammar, object model, SDK behavior, idempotency semantics, webhook signature format, and public error grammar do not change by mode.

| SLO area                 | Hosted commitment                                                                                                                       | Customer-validator commitment                                                                                                           | Self-hosted commitment                                                                                              | Pillar does not commit to                                                                       |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| API availability         | Pillar commits to API edge, API service, Postgres, queues, projection, webhook, participant integration, and status page.               | Pillar commits to Pillar API/runtime software and managed components; customer validator/participant availability is tagged separately. | Pillar commits to software/chart behavior, documented probes, and upgrade compatibility; customer operates runtime. | Customer network, customer-operated validator, customer cloud outage, customer DNS/TLS changes. |
| API latency              | Pillar commits to targets under published load profile and managed infra sizing.                                                        | Pillar commits excluding customer validator latency; participant-induced latency is surfaced with scoped labels.                        | Pillar provides reference targets and perf harness; customer owns capacity.                                         | Under-provisioned customer CPU/DB/queue/object storage.                                         |
| Intent acceptance        | Pillar commits to stable idempotency, operation creation, audit, and command enqueue semantics.                                         | Same, excluding customer participant unavailability after enqueue.                                                                      | Same software guarantee; operator must run required dependencies.                                                   | Customer misconfigured party entitlements or participant auth.                                  |
| Ledger command success   | Pillar commits to participant connectivity, command dedupe, completion tracking, and DAR compatibility for Pillar-operated participant. | Pillar commits to command construction/dedupe; customer owns participant health, party rights, and synchronizer access.                 | Pillar commits to chart/software behavior and diagnostics; customer owns ledger environment.                        | Canton network incidents outside Pillar control unless contracted.                              |
| Projection freshness     | Pillar commits to projection worker, DB, PQS/ledger stream integration, rebuild drills.                                                 | Pillar commits after customer validator emits updates; validator stream stalls are customer-scoped.                                     | Pillar commits to reproducible rebuild tooling and metrics; operator owns capacity and stream access.               | Customer disabled streams, blocked DB writes, unsupported topology changes.                     |
| Reconciliation integrity | Pillar commits to detection, alerting, evidence preservation, and correction workflow.                                                  | Same; customer-operated ledger evidence retrieval may be customer responsibility.                                                       | Same software invariant; customer owns running reconciliation schedules.                                            | Silent customer bypass of Pillar runtime or unsupported manual ledger mutation.                 |
| Webhook delivery         | Pillar commits to event creation from projection, signing, retry, DLQ, replay, and dispatcher capacity.                                 | Same if Pillar operates dispatcher; customer-owned network egress is separately tagged.                                                 | Pillar commits to dispatcher behavior; customer owns egress, DNS, certs, and endpoint reachability.                 | Customer endpoint 5xx/timeouts, firewall blocks, expired customer certificates.                 |
| Search/export/reporting  | Pillar commits to managed search/export workers, object storage, signed URLs, audit manifests.                                          | Pillar commits where workers/storage are Pillar-managed; customer storage/network failures are scoped.                                  | Pillar commits to software and reference sizing; customer operates storage and worker scale.                        | Customer object storage outage or unsupported retention policy.                                 |
| Onboarding               | Pillar commits to hosted onboarding workflow and sandbox availability.                                                                  | Pillar commits to guided validation and diagnostics; customer validator setup remains shared responsibility.                            | Pillar commits to docs, chart validation, and diagnostics; customer executes install.                               | Customer procurement, network allowlisting delays, local policy approvals.                      |
| Security/compliance      | Pillar commits to key lifecycle, audit trace, compliance decisioning, and managed secret rotation for hosted.                           | Shared responsibility for validator credentials and customer-controlled keys.                                                           | Software supports controls; customer operates KMS/Vault/IdP/network controls.                                       | Customer-operated key loss, IdP outage, disabled audit storage.                                 |
| Billing/usage            | Pillar commits to usage event emission and invoice generation for Pillar-billed hosted service.                                         | Pillar commits to usage collection for managed components; customer-reported validator costs may be out of scope.                       | Pillar commits to license/usage agent behavior where enabled.                                                       | Customer tampering with disabled metering agent or disconnected license channel.                |

Mode-specific alert labels:

| Label               | Hosted                                          | Customer-validator                                                                                | Self-hosted                                                                   |
| ------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `responsibility`    | `pillar` unless customer endpoint/client-caused | `pillar`, `customer_validator`, or `shared`                                                       | `customer_operator`, `pillar_software`, or `shared`                           |
| `status_page_scope` | Pillar publishes public component impact.       | Pillar publishes managed component impact and customer-validator advisory when customer-approved. | Customer owns public status; Pillar may publish software advisory.            |
| `budget_owner`      | Pillar SRE owner.                               | Pillar owner for managed path; customer owner label for validator failures.                       | Customer operator for runtime; Pillar product owner for software regressions. |
| `sla_eligible`      | Usually yes for contracted hosted SLAs.         | Only managed components and defined shared boundaries.                                            | Usually no runtime SLA unless support contract defines it.                    |

Commitment boundaries:

| Boundary                | Binding rule                                                                                                                                                   |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API grammar             | Identical across modes; any mode-specific public field or endpoint is a regression.                                                                            |
| Idempotency             | Same external intended change maps to same operation/command identity in every mode where Pillar runtime submits commands.                                     |
| Webhook signature       | Same `Pillar-Signature` semantics and replay model across modes.                                                                                               |
| Projection rebuild      | Rebuildability is mandatory across modes; operational execution ownership differs.                                                                             |
| Status semantics        | Hosted status is Pillar-published; customer-validator/self-hosted may publish customer-owned status but Pillar diagnostics must use the same state vocabulary. |
| Error budget accounting | Pillar-owned failures burn Pillar budget; customer-owned failures are tagged and reported but do not hide Pillar software defects.                             |
