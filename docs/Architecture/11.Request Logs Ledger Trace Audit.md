# Executive Summary

Pillar의 운영 추적성 시스템은 **RequestLog → LedgerTrace → AuditLog** 3계층으로 설계한다.

핵심 결정은 다음과 같다.

1. **RequestLog**는 외부 API 호출의 Stripe-grade 운영 로그다. `Request-Id`를 응답 헤더에 항상 반환하고, `Idempotency-Key`, API 버전, SDK, 요청/응답 해시, 마스킹된 파라미터, 에러, OTel trace ID를 저장한다. Stripe는 각 API 요청에 request identifier를 부여하고 Dashboard request log와 연결하며, 이벤트의 `request` 필드에 `request.id`와 `request.idempotency_key`를 포함할 수 있다. Pillar도 이 패턴을 채택한다. ([Stripe Docs][1])

2. **LedgerTrace**는 Pillar의 핵심 운영 증거 그래프다. 외부 고객에게는 Canton을 숨기되, 내부적으로는 `request_id → idempotency_key → intent_id → command_id → transaction_id → event_id → webhook_delivery_id`를 하나의 DAG로 연결한다. Canton/Daml 문서는 `WorkflowId`, `CommandId`, `SubmissionId`, `TransactionId`, `LedgerEventId`, `Trace/SpanId`, `LedgerOffset`를 주요 correlation identifier로 설명한다. Pillar는 이 ID들을 내부 trace spine으로 사용한다. ([Digital Asset Documentation][2])

3. **AuditLog**는 보안·컴플라이언스용 append-only ledger of actions다. RequestLog와 LedgerTrace가 “무슨 일이 일어났는가”를 보여준다면, AuditLog는 “누가, 어떤 권한으로, 어떤 정책 평가를 거쳐, 어떤 리소스에 접근하거나 변경했는가”를 증명한다.

4. **OpenTelemetry는 보조 관측 계층이지 감사 원장이 아니다.** OTel trace는 런타임 latency와 분산 시스템 디버깅에 사용하고, Pillar DB의 LedgerTrace는 무샘플링·장기보존·컴플라이언스 증거로 사용한다. OpenTelemetry는 traces, metrics, logs를 instrumenting/collecting/exporting하기 위한 vendor-neutral framework이고, context propagation을 통해 trace/log/metric을 서비스 경계에서 상관시킬 수 있다. ([OpenTelemetry][3])

# Goals / Non-goals

## Goals

### 1. End-to-end traceability

모든 사용자-facing mutation은 다음 spine으로 추적 가능해야 한다.

```text
request_id
  → idempotency_key
  → intent_id
  → command_id
  → transaction_id
  → event_id
  → webhook_delivery_id
```

단, 실제 시스템에서는 1:1 chain이 아니라 **DAG**다.

예시:

```text
req_123
  → idem_hash_abc
  → tin_001
  → cmd_transfer_submit_001
  → tx_001
  → ledger_event_001
  → evt_transfer_posted_001
  → whdel_endpointA_attempt1
  → whdel_endpointA_attempt2
  → whdel_endpointB_attempt1
```

### 2. Stripe-like external API

외부 API는 Canton을 노출하지 않는다.

외부 고객은 다음 개념만 본다.

```text
request_log
transfer
holding
balance
event
webhook_delivery
trace
```

Canton-native 필드는 role-gated internal expansion으로만 제공한다.

```http
GET /v1/transfers/tr_123/trace?expand[]=canton
```

### 3. Canton-native internal runtime

내부 runtime은 Canton/Daml의 correlation model을 정면으로 사용한다.

| Pillar concept    | Canton/Daml mapping                            |
| ----------------- | ---------------------------------------------- |
| `intent_id`       | `workflow_id`                                  |
| `command_id`      | Canton Ledger API `command_id`, retry 간 stable |
| `submission_id`   | retry attempt별 unique                          |
| `transaction_id`  | Ledger API update/transaction identifier       |
| `ledger_event_id` | transaction tree node / ledger event ID        |
| `ledger_offset`   | participant-local offset                       |
| `otel_trace_id`   | W3C/OTel trace ID                              |

Canton 문서는 `workflow_id`가 resulting transaction에 포함되어 여러 transaction으로 구성된 workflow tracking에 쓰일 수 있고, `command_id`는 command-completion correlation에 사용된다고 설명한다. Pillar는 `intent_id = workflow_id` 원칙을 채택한다. ([Digital Asset Documentation][8])

### 4. Audit-grade evidence

Pillar DB는 source of truth가 아니다. 그러나 다음은 DB에 보존한다.

```text
Projection / Audit / Config
```

즉, LedgerTrace는 “ledger-derived projection + audit evidence”이고, 원장 자체는 Canton이다.

### 5. Dashboard-first operations

운영자가 어떤 ID 하나만 알아도 전체 flow를 찾을 수 있어야 한다.

검색 가능한 ID:

```text
request_id
idempotency_key
intent_id
transfer_id
command_id
transaction_id
ledger_event_id
event_id
webhook_delivery_id
otel_trace_id
contract_id_hash
```

---

## Non-goals

1. **Pillar DB를 ledger substitute로 만들지 않는다.** LedgerTrace는 evidence graph이지 ledger state의 원본이 아니다.
2. **외부 API에 Canton contract-first model을 노출하지 않는다.** Contract ID, template ID, party visibility는 internal/debug expansion이다.
3. **OpenTelemetry sampling에 audit를 의존하지 않는다.** OTel trace가 drop되어도 LedgerTrace는 완전해야 한다.
4. **raw sensitive payload를 request log에 저장하지 않는다.** canonical hash + masked snapshot만 저장한다.
5. **Dashboard trace viewer가 Canton admin console을 대체하지 않는다.** 운영 디버깅에는 충분해야 하지만 topology/participant admin은 별도 권한 영역이다.

# Architecture

## Component overview

```text
Client / SDK / CLI
    │
    │ HTTP + Idempotency-Key + Pillar-Version + traceparent
    ▼
API Gateway / RequestLog Middleware
    │ creates request_id, request_log, audit shell
    ▼
Idempotency Service
    │ binds idempotency_key_hash → request_id → intent_id
    ▼
Intent Service
    │ creates intent_id, transfer_id, workflow_id
    ▼
Command Orchestrator
    │ creates command_id, submission_id, Canton command
    ▼
Canton Ledger API Client
    │ gRPC Ledger API / internal JSON Ledger API only
    ▼
Canton Participant / Synchronizer
    │ source of truth
    ▼
Completion + Update Consumers
    │ captures command completion, update_id, transaction_id, offset, ledger events
    ▼
Projection Engine
    │ balance/holding/transfer projection
    ▼
Event Engine
    │ creates evt_* from projection changes
    ▼
Webhook Dispatcher
    │ creates whdel_* delivery attempts
    ▼
Dashboard Trace Viewer / API / Compliance Export
```

## Three-log model

| Layer               | Object        | Purpose                                                              | Retention stance                    |
| ------------------- | ------------- | -------------------------------------------------------------------- | ----------------------------------- |
| API operations      | `RequestLog`  | API request/response observability                                   | medium-term, masked                 |
| Ledger evidence     | `LedgerTrace` | End-to-end causal graph across API, intent, Canton, events, webhooks | long-term, no raw sensitive payload |
| Compliance/security | `AuditLog`    | Actor/action/policy/resource evidence                                | long-term immutable/WORM            |

## ID vocabulary

| ID                    |           Generated by |                 External? |                                 Cardinality | Notes                                                  |
| --------------------- | ---------------------: | ------------------------: | ------------------------------------------: | ------------------------------------------------------ |
| `request_id`          |            API Gateway |                       Yes |                        one per HTTP request | Returned in `Request-Id` header.                       |
| `idempotency_key`     |           Client / SDK |               Yes, masked | optional per request, required for mutation | Stored as hash + preview.                              |
| `intent_id`           |         Intent Service |                       Yes |                     one per business intent | Primary business workflow anchor.                      |
| `transfer_id`         |           Transfer API |                       Yes |                     one per transfer object | User-facing resource ID.                               |
| `workflow_id`         |                Runtime |                  Internal |                 usually same as `intent_id` | Sent to Canton.                                        |
| `command_id`          |   Command Orchestrator |      Internal, role-gated |              one per logical ledger command | Stable across retries.                                 |
| `submission_id`       |   Command Orchestrator |                  Internal |                             one per attempt | Changes per retry.                                     |
| `transaction_id`      | Ledger Update Consumer |                Role-gated |                     zero or many per intent | Pillar alias for ledger update/transaction identifier. |
| `ledger_event_id`     | Ledger Update Consumer |                  Internal |                        many per transaction | Node/event identifier.                                 |
| `event_id`            |           Event Engine |                       Yes |                        many per transaction | External webhook event object.                         |
| `webhook_delivery_id` |     Webhook Dispatcher |                       Yes |                              many per event | Per endpoint attempt.                                  |
| `otel_trace_id`       |     OTel SDK / Gateway | Internal, support-visible |                   one per distributed trace | Runtime observability link.                            |

## Canonical trace spine

For a simple successful transfer:

```text
RequestLog(req_7Er...)
  └─ IdempotencyRecord(hash(idem_...))
      └─ TransferIntent(tin_9Qx...)
          └─ Command(cmd_3kP...)
              └─ LedgerTransaction(tx_8Bz...)
                  └─ LedgerEvent(levt_2Lh...)
                      └─ Event(evt_transfer_posted...)
                          └─ WebhookDelivery(whdel_1...)
```

For a failed ledger command:

```text
RequestLog(req_7Er...)
  └─ IdempotencyRecord(hash(idem_...))
      └─ TransferIntent(tin_9Qx...)
          └─ Command(cmd_3kP...)
              └─ Completion(status=FAILED)
                  └─ Event(evt_transfer_failed...)
                      └─ WebhookDelivery(whdel_1...)
```

For an async timeout:

```text
RequestLog(req_7Er..., response=202 processing)
  └─ Intent(tin_9Qx..., status=processing)
      └─ Command(cmd_3kP..., status=submitted)
          └─ Later Completion / Transaction / Event / Webhook
```

## Important architectural rule

**LedgerTrace must be built from durable internal records, not from sampled OTel traces.**

OTel spans are linked into LedgerTrace using:

```text
otel_trace_id
otel_span_id
traceparent
baggage
```

But if OTel sampling drops spans, LedgerTrace still remains complete because the DB records are written at every state transition.

# API / Object Model

## API grammar

Pillar trace APIs follow Stripe-style conventions.

```json
{
  "object": "list",
  "data": [],
  "has_more": false,
  "url": "/v1/request_logs"
}
```

Common query parameters:

| Parameter                       | Meaning                     |
| ------------------------------- | --------------------------- |
| `limit`                         | 1–100, default 10           |
| `starting_after`                | cursor pagination           |
| `ending_before`                 | reverse cursor pagination   |
| `created[gte]` / `created[lte]` | Unix timestamp filter       |
| `expand[]`                      | controlled expansion        |
| `livemode`                      | `true` / `false`            |
| `account`                       | platform/internal only      |
| `include[]`                     | selective internal sections |

Common headers:

```http
Request-Id: req_...
Pillar-Version: 2026-05-01
Idempotency-Key: <client-provided>
traceparent: <W3C trace context>
```

Stripe’s API design uses predictable REST URLs, JSON responses, standard HTTP codes, authentication, and verbs. Pillar should match that grammar from day one. ([Stripe Docs][6])

| Field               |          Stored raw? |            Displayed? | Notes                                                      |

It answers:

```text
Which external request caused this transfer?
Which idempotency key protected it?
Which intent was created?
Which Canton command was submitted?
```

### `transaction_id` naming rule

Canton/Daml API surfaces may use `updateId`, transaction identifiers, offsets, and event IDs depending on service/API version. Internal storage keeps both:

```text
transaction_id
```

This prevents external API churn if Canton naming evolves.

# Internal Runtime

## RequestLog middleware

Every API request executes this sequence before business logic.

```text
1. Parse auth.
2. Resolve account, livemode, API version.
3. Generate request_id.
4. Extract or create traceparent.
5. Canonicalize request body.
6. Mask body/headers.
7. Insert request_log row with status=in_progress.
8. Proceed to idempotency/business logic.
9. Update request_log with response summary, object links, error, duration.
10. Emit audit event when policy requires.
```

Mutation request without durable `request_log` insert must fail closed:

```text
503 service_unavailable
```

Rationale: a ledger-affecting operation without a request log violates Pillar’s traceability invariant.

## Idempotency service

### Key rules

1. `Idempotency-Key` is required for high-value POST endpoints.
2. Store only:

```text
account_id
key_hash
key_preview
method
path_template
canonical_request_hash
first_request_id
intent_id
status
expires_at
```

3. Same key + same request hash returns the original result.
4. Same key + different request hash returns:

```http
409 Conflict
```

```json
{
  "error": {
    "type": "idempotency_error",
    "code": "idempotency_key_reused",
    "message": "This idempotency key was already used with different request parameters.",
    "request_id": "req_..."
  }
}
```

Stripe’s idempotency model supports safe retries for create/update operations and uses the `Idempotency-Key` header for POST requests; Pillar mirrors the grammar but extends the trace retention window for ledger evidence. ([Stripe Docs][4])

## Intent creation

For `POST /v1/transfers`:

```text
transfer_id = tr_*
intent_id   = tin_*
workflow_id = intent_id
```

The API returns immediately once the intent is durably created and the command is queued/submitted.

```json
{
  "id": "tr_01HY8Y8J...",
  "object": "transfer",
  "status": "processing",
  "trace": {
    "request_id": "req_...",
    "ledger_trace": "ltr_..."
  }
}
```

## Command orchestration

### Command ID construction

`command_id` must be stable across retries.

Recommended format:

```text
cmd_<base32(sha256(account_id + intent_id + command_type + command_version))>
```

Example:

```text
cmd_DHF7K3Q2J9M7BTY6BNR4ZJQ5
```

### Submission ID construction

`submission_id` is unique per attempt.

```text
sub_<ulid>
```

### Canton command metadata

```text
application_id = pillar-runtime-{env}
workflow_id    = intent_id
command_id     = stable command ID
submission_id  = per-attempt ID
act_as         = internal party set
read_as        = internal party set if needed
```

Canton command deduplication is based on the change ID, which includes submitting parties, user ID, and command ID. The docs note deduplication is only guaranteed if commands are submitted to the same Participant Node. ([Digital Asset Documentation][8])

Therefore Pillar must enforce:

```text
account_id / asset_network / party set
  → deterministic participant routing
```

Otherwise a retry could bypass participant-local deduplication.

## Completion consumer

Consumes command completions and updates:

```text
command.status
completion.status
completion.error_code
completion.error_message_masked
transaction_id if available
ledger_offset
```

If command completion succeeds but projection is delayed:

```text
ledger_trace.status = committed_projection_pending
```

## Update / transaction consumer

Consumes committed ledger updates and records:

```text
ledger_update_id
transaction_id
workflow_id
command_id
offset
effective_at
record_time
synchronizer_id
ledger_event_ids
contract_id_hashes
template IDs
choices
projection object links
```

The JSON Ledger API OpenAPI includes `traceContext`, and describes it as corresponding to trace context supplied by the client application in the original command submission header. Pillar should propagate OTel context into ledger submissions and store the returned trace context where available. ([Digital Asset Documentation][12])

## Projection engine

Projection remains balance/holding-first.

```text
Ledger event
  → projection delta
  → transfer status
  → holding balance update
  → event creation
```

External customers see:

```text
transfer.succeeded
holding.available_amount changed
balance updated
```

They do not see:

```text
Daml template
contract ID
choice node
stakeholder party graph
```

unless explicitly granted internal diagnostic access.

## Event engine

Pillar event object should include Stripe-style request linkage.

```json
{
  "id": "evt_01HY8Y9V...",
  "object": "event",
  "type": "transfer.succeeded",
  "created": 1779782420,
  "request": {
    "id": "req_01HY8Y6V...",
    "idempotency_key": "idem_...8f2a"
  },
  "data": {
    "object": {
      "id": "tr_01HY8Y8J...",
      "object": "transfer",
      "status": "succeeded"
    }
  }
}
```

Stripe’s Event object includes request metadata with request ID and idempotency key, which is directly applicable to Pillar’s webhook-first workflow. ([Stripe Docs][13])

## Webhook dispatcher

For each event and endpoint:

```text
event_id
endpoint_id
delivery_id
attempt_no
payload_hash
signature_id
request_started_at
response_status
response_body_hash
status
next_retry_at
```

Webhook delivery status:

```text
pending
delivering
delivered
failed
retry_scheduled
exhausted
disabled_endpoint
```

Recommended retry policy:

| Window        | Behavior                    |
| ------------- | --------------------------- |
| Immediate     | 0s, 30s, 2m                 |
| Short         | 10m, 30m, 1h                |
| Long          | exponential up to 72h       |
| Manual replay | allowed for retained events |

Stripe retries failed webhook deliveries for up to three days and provides guidance for manually processing undelivered events; Pillar should match that expectation unless asset-network regulations require longer delivery replay. ([Stripe Docs][14])

# Failure Modes

## 1. RequestLog insert failure

### Scenario

API Gateway cannot persist minimal request log.

### Behavior

| Request type          | Behavior                                                              |
| --------------------- | --------------------------------------------------------------------- |
| Mutation              | Fail closed with `503 service_unavailable`.                           |
| Read                  | Allow only if policy permits non-audited read; otherwise fail closed. |
| Internal health check | Can bypass with separate operational log.                             |

### Reason

A Canton-affecting operation without request trace violates Pillar’s traceability invariant.

---

## 2. Duplicate idempotency key, same request

### Scenario

Client retries after network timeout.

### Behavior

Return original response or current object state.

```json
{
  "id": "tr_...",
  "object": "transfer",
  "status": "processing",
  "trace": {
    "request_id": "req_original",
    "current_request_id": "req_retry"
  }
}
```

---

## 3. Duplicate idempotency key, different request body

### Behavior

```http
409 Conflict
```

```json
{
  "error": {
    "type": "idempotency_error",
    "code": "idempotency_key_reused",
    "message": "This idempotency key was already used with different request parameters.",
    "request_id": "req_..."
  }
}
```

---

## 4. API response timeout after command submission

### Scenario

Command submitted to Canton, but API worker times out.

### Behavior

1. RequestLog status:

```text
response_status = 202 or timeout
ledger_trace.status = submitted
```

2. Client retry with same idempotency key returns current transfer state.
3. Webhook eventually emits `transfer.succeeded` or `transfer.failed`.

Stripe’s error guidance treats connection errors as indeterminate and recommends idempotency plus object retrieval or webhook observation to learn final outcome; Pillar should use the same customer-facing behavior. ([Stripe Docs][15])

---

## 5. Canton command rejected

### Scenario

Ledger command completion returns failure.

### Behavior

```text
ledger_trace.status = failed
transaction_id = null
completion_error_code = ...
transfer.status = failed
event = transfer.failed
```

Dashboard must show:

```text
Request accepted → Intent created → Command submitted → Command rejected → Event emitted
```

---

## 6. Ledger committed, projection consumer lagging

### Scenario

Canton transaction committed, but projection engine has not updated transfer/holding view.

### Behavior

```text
ledger_trace.status = committed_projection_pending
transfer.status = processing
```

Dashboard warning:

```text
Ledger commit observed. Projection is behind offset 00000000000001234567.
```

Recovery:

```text
Replay projection from last durable offset.
```

---

## 7. Projection exists, trace edge missing

### Scenario

Projection engine updates transfer, but trace edge insert failed.

### Behavior

```text
ledger_trace.status = reconciling
```

Repair job reconstructs edges from:

```text
workflow_id
command_id
transaction_id
ledger_event_id
projection_object_id
```

---

## 8. Webhook delivery failure

### Scenario

Endpoint returns non-2xx or timeout.

### Behavior

```text
webhook_delivery.status = retry_scheduled
event.delivery_success = false
ledger_trace.webhook_status = partially_delivered
```

Dashboard actions:

```text
Retry now
Disable endpoint
Replay event
View signature base string hash
```

Do not mark transfer failed because webhook failure does not change ledger truth.

---

## 9. OTel trace missing

### Scenario

Sampling dropped trace or collector unavailable.

### Behavior

```text
ledger_trace.otel.sampled = false
```

No loss of audit completeness. The DB trace graph remains canonical.

---

## 10. Audit hash-chain mismatch

### Scenario

Audit verifier detects broken hash chain.

### Behavior

```text
severity = critical
freeze compliance exports
emit security.audit_integrity_failed
page security/on-call
```

---

## 11. Multi-participant retry hazard

### Scenario

Retry goes to different Canton Participant Node.

### Risk

Canton docs state command deduplication is only guaranteed when commands are submitted to the same Participant Node. ([Digital Asset Documentation][8])

### Mitigation

```text
Deterministic participant routing
account/party affinity
retry routing lock
participant failover policy with reconciliation
```

# Security / Compliance

## Sensitive field masking

### Principles

1. **Mask before persistence.**
2. **Hash before masking only for canonical proof.**
3. **Never store secrets raw.**
4. **Allow role-gated unmasking only from source systems, not request logs.**
5. **Audit every sensitive expansion.**

### Masking registry

Field paths:

```yaml
always_redact:
  - headers.authorization
  - headers.api-key
  - headers.pillar-signature
  - request.private_key
  - request.seed_phrase
  - request.ssn
  - request.tax_id
  - request.bank_account_number
  - request.card_number

hash_only:
  - headers.idempotency-key
  - request.external_reference
  - request.memo
  - request.customer.email
  - request.customer.phone

partial:
  - request.customer.name
  - request.address.postal_code
```

### Ledger payload masking

Canton contract payloads may contain sensitive business data. Pillar must store:

```text
template_id
choice
contract_id_hash
witness_parties_hash
raw_event_hash
projection object link
```

By default, not:

```text
full contract payload
party names
raw contract IDs
PII
```

## Retention baseline

Recommended default retention:

| Data                                            |                   Default | Notes                                |
| ----------------------------------------------- | ------------------------: | ------------------------------------ |
| Idempotency active response cache               |               24h minimum | Stripe-like retry guarantee.         |
| Idempotency hash linkage                        |                   90 days | For support and trace lookup.        |
| RequestLog masked detail                        |                   90 days | Dashboard debugging.                 |
| RequestLog summary                              |                 13 months | Trend/error analysis.                |
| Webhook delivery payload/response masked detail |                   30 days | Replay/debug window.                 |
| Webhook delivery summary                        |                 13 months | Delivery health evidence.            |
| LedgerTrace                                     |                   7 years | No raw sensitive payload by default. |
| AuditLog                                        |           7 years minimum | WORM/legal hold capable.             |
| Compliance export artifact                      | 7–30 days download window | AuditLog records creation/download.  |
| Hash-chain proof                                |          same as AuditLog | Integrity verification.              |

Regulated asset networks may require longer retention. Treat the table as a platform default, not legal advice.

## Access control

Roles:

| Role               | Capabilities                                        |
| ------------------ | --------------------------------------------------- |
| `developer`        | View own request logs, masked traces.               |
| `support`          | View masked transfer traces with support reason.    |
| `ops`              | View internal runtime status and OTel links.        |
| `ledger_ops`       | View Canton identifiers and ledger event metadata.  |
| `compliance`       | Create/download masked compliance exports.          |
| `compliance_admin` | Approve regulated unmasked exports.                 |
| `security_admin`   | View audit integrity alerts and break-glass events. |

Every Dashboard access to trace/audit data emits an `AuditLog`.

## Encryption

Minimum:

```text
TLS in transit
KMS envelope encryption at rest
per-environment keys
per-tenant keys for enterprise plans
separate key domain for compliance exports
secret material excluded from logs
```

## Compliance export controls

Compliance exports must include:

```text

requesting actor
approval chain
reason code
time range
object range
schema version
redaction report
manifest hash
archive hash
download audit events
expiry timestamp
```

For `regulated_unmasked` mode:

```text

download watermark
mandatory legal/compliance reason

```

# Open Questions

1. **Retention jurisdiction**
   Should LedgerTrace retention be fixed at 7 years, or asset-network configurable by jurisdiction and regulated asset class?

2. **External visibility of transaction IDs**
   Should `transaction_id` be visible to all customers, or only to enterprise/support roles?

3. **Contract ID exposure**
   Should contract IDs ever be shown raw in Dashboard, or always as hashes with Daml Shell deep-link available only to internal ledger operators?

4. **Workflow ID strategy**
   Default recommendation is `workflow_id = intent_id`. For multi-step workflows, should we use one workflow ID across all commands or one workflow ID per transfer leg?

5. **Idempotency retention**
   Stripe-like public guarantee can be 24h, but ledger-backed transfers may need longer support windows. Should enterprise tenants get 7-day or 30-day idempotency records?

6. **Webhook retry window**
   Should Pillar exactly mirror 72h automatic retry, or offer configurable retry windows per endpoint?

7. **OTel backend**
   Should managed Pillar standardize on Tempo/Jaeger internally, or expose OTLP export to customer-owned observability stacks?

8. **Compliance export approval**
   Is dual approval required for all exports, or only `regulated_unmasked` exports?

9. **Participant routing**
   What is the canonical routing key for Canton participant affinity: account, party, asset network, or holding?

10. **Sandbox determinism**
    Canton sandbox party IDs may change between restarts when keys are generated randomly. Should Pillar sandbox persist participant keys to keep trace demos stable? Daml docs note sandbox party suffixes can change on restart due to random key generation. ([Digital Asset Documentation][20])
